# Java 场景题

## 电商平台中订单未支付过期如何实现自动关单？

### 轻量级解决方案
- **实现原理**：使用JDK的延迟队列将订单按超时时间排序，到期的订单在内存中进行关单。
- **优点**：不依赖其他的中间件或数据库，能实现毫秒级的精度控制。
- **缺点**：所有的数据都存储在JVM内存中，重启服务会导致数据的丢失。并且当订单数据量非常大时，会引发OOM。且在集群模式下多节点服务会导致数据重复处理。
- **适用场景**：仅适用于单机部署的内部系统或低频业务。

### 分布式解决方案
- **实现原理**：基于Redis实现处理逻辑，将订单的ID作为key存入缓存，监听key的过期事件来触发关单操作。
- **优点**：利用了Redis的高性能，并支持分布式架构。
- **缺点**：Redis的惰性删除策略可能会导致关单延迟；此外消息没有持久化处理，如果订阅者宕机的话会丢失正在处理的事件。
- **适用场景**：可以容忍秒级延迟且可以接受偶发消息丢失的非核心业务。
- **改进方案**：基于Redis的ZSet结构实现分布式队列 Redisson，订单按超时时间戳排序，后台线程拉取到期任务。

### 工业级方案
- **实现原理**：利用消息中间件的死信队列进行处理，消息到期后转入死信队列，消费者进行处理关单。
- **优点**：支持集群消费和重试机制，消息零丢失
- **缺点**：队头消息阻塞会导致后续消息发生延迟，丢失处理精度
- **适用场景**：需要高吞吐量、高可靠性和业务解耦的大型平台

## 如果你的系统的QPS突然提升10倍你会怎么设计？

- 首先需要考虑到服务器的水平扩展能力，能通过云服务实现自动扩容。其次需要优化数据库的连接池，增大连接数并缩短超时时间防止连接耗尽，并实现数据库的读写分离，避免大流量下的主库过载。
- 其次将非核心操作解耦异步化，避免主要流程阻塞。同时优化批量操作减少网络开销。
- 最后为了避免大流量冲垮服务，可以通过令牌桶等机制进行限流，并在高并发情况下对某些非核心功能做熔断或降级处理。

## 如何设计一个支持10万QPS的会员系统？

需要使用分布式分层架构、缓存策略、数据库优化、异步处理及容灾机制等技术。

### 分布式分层架构
- 在网络接入层使用Load Balancer进行轮询分发流量，避免单点故障导致服务不可用
- 使用 API 网关统一管理入口
- 将会员系统拆解成独立的服务模块，便于水平扩展
- 服务与服务之间通过消息队列进行解耦
- 服务内部采用异步编程来处理IO密集型操作，提高线程利用率

### 缓存策略
- 设计多级缓存架构如 本地缓存 + 分布式缓存 + 数据库 的组合
- 利用Cache-Aside策略+延时双删的方式来避免并发脏读

### 数据库优化
- 采用分库分表与读写分离的方式提高数据库性能

## 短URL生成器设计：百亿短URL怎么做到无冲突？

- 在上线前先**离线生成**144亿个短URL（约86.4GB文件）存储于HDFS中，避免实时Hash冲突检测的性能瓶颈。且预生成时可以使用布隆过滤器来保证生成的URL没有重复，并且在这个短URL池使用率>80%时异步补充新的短码。在写入数据库时再进行一次唯一性校验，冲突时可以要求重试。
- 分布式唯一ID可以采用**雪花算法**来生成全局唯一长整型ID（时间戳+机器ID+序列号），再通过Base62编码（0-9a-zA-Z）转换为短字符串。这种编码方式可以支持568亿种组合，完全满足需求。
- 出于**安全**考虑，短码的长度应该要大于等于6位，避免被撞库。
