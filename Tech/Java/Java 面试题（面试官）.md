## 基础题

### HashMap 为什么非线程安全？并发场景应使用哪个类？

**解答：**
HashMap 在扩容时，如果多个线程同时进行修改链表结构，可能导致链表成环，造成死循环。JDK 1.8改用了尾插法，解决了死循环的问题。

另外 HashMap 的并发put操作可能会导致数据丢失。

并发安全的 Map 类有 **ConcurrentHashMap**，同级的类还有：ConcurrentLinkedDeque、CopyOnWriteArrayList、LinkedBlockingQueue 等。

### Java 的内存模型及常见的垃圾收集器

**内存区域：**

```
┌──────────────────────────────────┐
│              堆（Heap）           │
│  ┌─────────────┬──────────────┐  │
│  │   新生代     │    老年代     │  │  线程共享
│  │ ┌────┬──┬──┐│              │  │
│  │ │Eden│S0│S1││              │  │
│  └─┴────┴──┴──┴┴──────────────┘  │
│         元空间（Metaspace）        │
└──────────────────────────────────┘
┌──────────────────────────────────┐
│              栈（Stack）          │
│  局部变量表 | 操作数栈 | 动态链接  │  线程私有
│  程序计数器（PC Register）        │
│  本地方法栈（Native Method Stack）│
└──────────────────────────────────┘
```

| 区域 | 作用 | 特点 | GC |
|------|------|------|----|
| **堆（Heap）** | 存放对象实例 | 线程共享，JVM最大内存区域 | Yes |
| **新生代** | 新创建的对象 | Eden:S0:S1 = 8:1:1 | Minor GC |
| **老年代** | 长期存活对象 | 经过多次GC存活的对象 | Major GC |
| **元空间** | 类元数据、常量池 | 替代JDK 1.7的永久代，使用本地内存 | Yes |
| **栈** | 方法调用、局部变量 | 线程私有，-Xss设置大小 | No |
| **程序计数器** | 当前线程执行的字节码行号 | 唯一不会OOM的区域 | No |

**常见垃圾收集器：**
- **Serial GC**：单线程，适合小应用
- **Parallel GC**：多线程，吞吐量优先（JDK 8默认）
- **CMS**：并发标记清除，低停顿
- **G1**：分区回收，可预测停顿（JDK 9+默认）
- **ZGC**：超低延迟（< 10ms）

**扩展 — 如何排查内存泄露：**

常见原因：
- 集合类持有对象引用未清理
- 静态集合持有大量对象
- 监听器/回调未注销
- ThreadLocal未清理
- 数据库连接/IO流未关闭

### Java 线程池 ThreadPoolExecutor 的工作流程和核心参数

**工作流程：**

```
提交任务
     ↓
核心线程数未满？ ──Yes→ 创建核心线程执行
     ↓ No
队列未满？ ──Yes→ 放入队列等待
     ↓ No
最大线程数未满？ ──Yes→ 创建非核心线程执行
     ↓ No
执行拒绝策略
```

**构造参数：**

```java
public ThreadPoolExecutor(
    int corePoolSize,        // 核心线程数
    int maximumPoolSize,     // 最大线程数
    long keepAliveTime,      // 非核心线程空闲存活时间
    TimeUnit unit,           // 时间单位
    BlockingQueue<Runnable> workQueue,  // 任务队列
    ThreadFactory threadFactory,        // 线程工厂
    RejectedExecutionHandler handler    // 拒绝策略
)
```

## 场景题

### 题目一：物流追踪系统性能问题诊断

**背景：** 某类有以下特点：
1. 超过2400行代码
2. 注入了20多个依赖
3. 其中有一个方法使用大包号集合查询所有关联小包信息，包含：数据库查询、第三方API调用、缓存更新、MQ推送

**问题现象：**
1. 方法响应时间从200ms增加到了5s
2. 数据库连接池经常耗尽
3. 用户反馈页面卡顿

**可能原因及改进方案：**

1. **第三方API调用包含在事务内，阻塞了整个方法**
   - 改进：将阻塞的操作移至事务外

2. **所有操作串行处理，没有并发优化**
   - 改进：将操作按IO密集型/计算密集型分开进行并发处理

3. **数据库查询存在N+1问题（循环查询）**
   - 改进：去除循环查询，先计算查询条件，再批量查询

4. **大数据量查询未做数据分片**
   - 改进：根据数据库表大小设置合适的分片大小进行分片查询

5. **缓存大量穿透，大量查询漏到数据库**
   - 改进：使用布隆过滤器和锁等机制减少缓存穿透现象

6. **类违反单一职责原则，难以优化**
   - 改进：基于 SOLID 原则进行方法重构
     1. **S** - 单一职责：每个类只负责一件事
     2. **O** - 开闭原则：对内修改封闭，对外扩展开放
     3. **L** - 里氏替换：可以用任何子类替换对象，方便UT mock
     4. **I** - 接口隔离：各组件接口功能明确
     5. **D** - 依赖倒置：针对抽象（接口）编程而非具体实现
